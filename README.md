# Browser Diagnostics Companion

A Chrome extension (Manifest V3) that turns the browser itself into a lightweight diagnostics tool. It watches the active tab in real time and surfaces the three things a support/QA engineer usually digs for by hand in DevTools: console errors and warnings, failed network requests, and page performance timing — then lets you export it all as a single JSON report.

## Features

- **Console Issues** — captures `console.error` / `console.warn` calls, uncaught exceptions, and unhandled promise rejections from the page, with message, source, level, and timestamp.
- **Failed Requests** — tracks every HTTP request the tab makes and flags 4xx/5xx responses and hard network errors (DNS failures, connection refused, blocked requests, etc.), with URL, method, and status.
- **Performance** — reports page load time, DOMContentLoaded time, time-to-first-byte, and the slowest resource loads, using the Navigation Timing and Resource Timing APIs.
- **Live popup UI** — three tabbed sections (Console Issues, Failed Requests, Performance), each with a live count badge, dark devtools-style theme.
- **Export Report** — compiles everything captured for the current tab into one JSON file and downloads it.
- **Clear** — wipes captured data for the current tab so you can start a clean capture.
- Diagnostics automatically reset whenever the tab navigates to a new page, so a report always reflects the page currently open.

## How it works (architecture)

| File | Role |
|---|---|
| `injected.js` | Runs in the page's own JS context ("main world"). Patches `window.console.error`/`.warn`, listens for `error`/`unhandledrejection` events, and reads `performance.getEntriesByType(...)`. Posts everything via `window.postMessage`. |
| `content.js` | Runs in the extension's isolated content-script world on every page. Injects `injected.js` into the main world and relays its `postMessage` events to the background service worker via `chrome.runtime.sendMessage`. |
| `background.js` | The MV3 service worker. Stores per-tab diagnostics in `chrome.storage.session`, listens to `chrome.webRequest` for failed requests, resets a tab's data on new navigations (`chrome.webNavigation`), and answers the popup's requests for data, clearing, and report export. |
| `popup.html/js/css` | The UI. Fetches the active tab's data from the background worker, renders the three panels, and wires up Clear / Export Report. |
| `lib/` | Pure, framework-independent data-processing functions (no `chrome.*` calls) used by both the extension runtime and the unit tests. |

### Chosen approach for console capture, and why

MV3 removes the ability for a background page to run persistently, and an isolated-world content script **cannot** intercept `console.error`/`console.warn` calls made by the page's own scripts — isolated worlds get a separate copy of `window`/`console` from the page. The reliable way to intercept the page's real console calls is to inject a script into the page's **main world** (`injected.js`) that monkey-patches `window.console.error`/`.warn` directly, then relay captured messages back out through `window.postMessage` to the isolated-world content script, which forwards them to the background service worker.

This was chosen over the `chrome.debugger` (DevTools Protocol) API because `chrome.debugger` requires attaching a debugger session to the tab, which pops Chrome's "this extension is debugging this browser" banner and is disruptive for something meant to run passively in the background — a poor fit for a lightweight diagnostics companion.

### Known limitations of this approach

- **Race on early errors**: the content script runs at `document_start` and injects the main-world script as early as possible, but there is an unavoidable moment where the page has started running before the patch is installed. Console calls made in that window (e.g. very first synchronous script tag) can be missed.
- **Iframes**: only the top frame is instrumented (`all_frames: false`). Errors originating purely inside cross-origin iframes are not captured.
- **Native/browser-generated console entries**: some things DevTools shows in the Console (certain CSP violation notices, mixed-content warnings, some resource-load failures) are generated by the browser engine itself, not via a `console.error()` call, so they cannot be intercepted by patching the console object. The extension does capture uncaught exceptions and unhandled promise rejections separately via `window.addEventListener('error'/'unhandledrejection')`, which covers most of that gap, but not all of it.
- **Extension/DevTools context**: console output from other extensions' content scripts, or from the DevTools console itself when a user manually evaluates an expression, is not visible to this extension.
- **Service worker restarts**: MV3 service workers are terminated when idle. Captured data is kept in `chrome.storage.session` (survives worker restarts within the browser session, never touches disk) rather than in-memory, specifically to avoid losing data when the worker is recycled.

## Permissions explained

| Permission | Why it's needed |
|---|---|
| `activeTab` | Lets the popup identify and act on the tab the user currently has open, without requesting standing access to browsing history. |
| `scripting` | Used to inject the content script's supporting logic into the page context. |
| `webRequest` | Required to observe outgoing requests for the tab and detect failures (network errors, 4xx/5xx responses) — this cannot be done from a content script alone. |
| `webNavigation` | Used to detect when a tab starts a new top-level page load, so captured diagnostics can be reset per-page rather than mixing data from different pages together. |
| `downloads` | Used by the "Export Report" button to save the compiled JSON report to disk. |
| `storage` | Used to persist each tab's captured diagnostics in `chrome.storage.session` so data survives service-worker restarts during the browsing session. |
| `host_permissions` (`http://*/*`, `https://*/*`) | Required for `webRequest` to actually observe network traffic, and for the content script to auto-run at `document_start` on every page (rather than only after the user manually opens the popup), so console capture starts as early as possible. No data ever leaves the browser — everything stays local to `chrome.storage.session` until you explicitly export it. |

## Load it as an unpacked extension (for testing/demo)

1. Open `chrome://extensions` in Chrome.
2. Enable **Developer mode** (toggle in the top-right corner).
3. Click **Load unpacked**.
4. Select the `browser-diagnostics-companion` folder (this directory).
5. The extension icon appears in the toolbar. Pin it for easy access.
6. Open any regular `http(s)://` page, then click the extension icon to see captured diagnostics for that tab.

## Running the unit tests

The pure data-processing logic in `lib/` (performance summarization, request classification, report compilation) has no `chrome.*` dependency and is tested independently under Node's built-in test runner.

```bash
npm test
```

This runs `node --test tests/*.test.js` — no build step or external test framework required.

## Manual verification checklist

1. Load the extension unpacked (see above).
2. Visit a page that logs console errors/warnings (e.g. open DevTools console on any site and run `console.error('test error')`, or visit a page with a known broken script/API call).
3. Open the popup — the **Console Issues** tab and its badge should reflect what you saw in DevTools.
4. Visit a page that makes a request to a non-existent endpoint or returns a 404/500 — check the **Failed Requests** tab.
5. Check the **Performance** tab for page load time, DOMContentLoaded, and the slowest resources.
6. Click **Export Report** — confirm a `.json` file downloads and that it parses as valid, complete JSON with `consoleIssues`, `networkRequests`, and `performance` sections.
7. Click **Clear** — confirm all three panels reset to empty and badges return to 0.
